## 1. 目标与非目标

### 1.1 目标（Phase 1，开学前）

1. **身份解耦**：全局角色收敛为 `super_admin / user` 两级；「学员/导生」变成营期内任职记录，结营留档。
2. **营期类型化**：`category` 四类封闭枚举 + 类型行为配置；本期只实现培训营行为。
3. **教学周期**：营期挂 `term`（无起止日期，纯分组标签）。
4. **营期状态机**：`draft → upcoming → active → archived` 四态（对应产品语言：草稿/待开放/开营中(含选择阶段)/已结营），待开放营对全体可见。
5. **导生招募与双选简化**：待开放期「报名成为导生 + 老师审批 + 装饰名片」；开营期「学员报名 + 单轮 3 志愿」；老师「导出 CSV → 线下调剂 → 批量指派」。
6. **课程独立、进度绑营**：移除 `/userCourse/enroll` 自主加入与前端「加入学习」按钮；学习入口只剩营期选课。
7. **权限收敛**：`camp_role` 装饰器从「查全局 role」改为「查营内任职」；admin 端只留 super_admin。

### 1.2 非目标（本期明确不做）

- 系统内导生轮次反选、自动调剂（A8：线下完成）
- 换组流程（A12）
- 项目营/临床调研营/比赛营的实现（只做模型预留）
- 学习进度跨期留档改造（Q15，推迟）
- 等级评价系统、干事体系、个人主页、搜索、感谢信模板、站内信（Phase 3+）
- `check_record.camp_session_id` 落实写入（维持日期范围间接归属，已知债不动）

## 2. 总体模型

```
User ──(role: super_admin | user)──────────────────────────┐
  │                                                        │
  │  营内任职（多对多，含角色/来源/任期/评价预留）              │
  └──► camp_member ──► camp_session ◄── term（教学周期，纯标签）
           │  role: student/mentor/…          │  category: training/project/research/competition
           │  team_mentor_id（培训营学员→导生） │  status: draft/upcoming/active/archived
           ▼                                   │
      camp_group（kind=direction 大组）          ├──► camp_course ──► course（独立实体，独立页面维护）
                                                ├──► camp_join_request（统一报名：apply_role）
                                                └──► camp_ms_*（志愿/名片，单轮化）

权限真相源：全局 = user.role；营内 = camp_member 行（不再看 user.role）
```

核心思想一句话：**「你是谁」只有两级；「你在某次活动里担任什么」是营期下的任职记录，随营期归档永久留痕**——这就是未来等级评价系统的数据底座。

## 3. 数据模型

约定：沿用现有迁移机制（无 Alembic，`scripts/migrate/migrate_10_*.py` + 手工执行，见 §7）。以下仅列**变更**；未提及的表不动。

### 3.1 User：全局角色收敛

| 变更 | 内容 |
|---|---|
| `role` 枚举收敛 | 只剩 `super_admin / user`。存量刷新：`teacher → super_admin`，`mentor / student → user` |
| `+ admin_tag` | `VARCHAR(20) NULL`，取值 `teacher / developer`，**仅用于审计日志与界面显示**，无任何权限语义（§4.1） |
| `user_mode` | **退役并删列**（2026-09-01 决策，推翻初稿「保留双写」）：全站约 48 处裸 `user_mode` 门禁一次性清账（§4.3），models 定义、seed 造号、登录/用户接口 payload 全清，migrate_10 删列 |
| `ROLE_RANK` | 退化为 `{'super_admin': 1, 'user': 0}`；`is_staff()` 重定义为 `role=='super_admin'`（函数名保留，避免全量改 import）；`has_role_at_least()` 标记 deprecated |

新增唯一管理入口：`PUT /admin/users/<id>/role`（super_admin 专用，可设 super_admin/user 与 admin_tag）——现状全系统**没有任何修改 role 的端点**，不补这个端点就没法任命新老师/开发（见 §5、§6）。

### 3.2 term（新表，教学周期）

```python
class TermModel(db.Model):
    id, code(UNIQUE, '2026-autumn'), name('2026 秋季学期'), created_at
```

- 一年固定四段：`winter / spring / summer / autumn`，**无起止日期**（A1）。
- 建营时下拉选择 + 允许 super_admin 行内新建（只填 code/name）。
- 用途：营期列表按学期分组、已结营归档浏览、未来等级系统按学年统计。
- 迁移时为存量营期补一条 `2026-summer`。

### 3.3 camp_session：类型与状态

| 变更 | 内容 |
|---|---|
| `+ category` | `VARCHAR(20) NOT NULL DEFAULT 'training'`；存量全部回填 `training` |
| `+ term_id` | FK `term.id`，可空（历史数据兜底），新建营期必填（接口校验） |
| `camp_type` | **退役**：列保留一版便于回滚，代码停止读写，下个大版本删除 |
| `status` | 四态：`draft / upcoming / active / archived`（新增 `upcoming`） |
| `ms_*` 时间轴 | `ms_preference_start / ms_preference_deadline` 保留（单轮志愿窗口）；`ms_round1_deadline / ms_round2_deadline` 退役（列保留，代码停读） |
| 其余字段 | `expected_check_in / min_daily_hours / weekdays_only / is_featured / mentor_selection_enabled / ms_tags` 全部不动 |

**状态机**（触发者均为 super_admin，`_camp_writable` 继续拦 archived 写入）：

```
draft ──发布──► upcoming ──开营──► active ──结营──► archived
 (仅管理员可见)   (全员可见卡片)     (报名/志愿/选课/考勤)   (只读留档)
        ▲            │
        └──撤回发布───┘
```

产品语言映射：待开放=upcoming；选择阶段=active 早期（报名与志愿窗口内）；正在开营=active；已结营=archived。

各态允许的动作（培训营）：

| 动作 | draft | upcoming | active | archived |
|---|---|---|---|---|
| 管理员编辑营期信息 | ✓ | ✓ | ✓(受限) | ✗ |
| 学员浏览营期卡片 | ✗ | ✓ | ✓ | ✓(参与过的人) |
| **报名成为导生**（apply_role=mentor） | ✗ | ✓ | ✗（开营后由后台拉人） | ✗ |
| 导生装饰名片 | ✗ | ✓（审批通过后） | ✓ | ✗ |
| 学员报名入营（apply_role=student） | ✗ | ✗ | ✓ | ✗ |
| 提交 3 志愿 | ✗ | ✗ | ✓（志愿窗口内） | ✗ |
| 老师导出志愿 / 批量指派 | ✗ | ✗ | ✓ | ✗ |
| 选课 / 考勤 / 请假 / 奖励 | ✗ | ✗ | ✓ | ✗ |

可见性规则变更：`GET /camp/sessions` 对普通用户返回 **upcoming + active 全部** + **自己参与过的 archived**（现状只返回参与过的非 draft）。`is_featured` 招募指针语义不变（CampHome 着陆页指向）。

### 3.4 类型行为配置（附录全文）

`category` 的差异**写死为代码内配置常量**，不做可视化配置（A2、「不用做得太智能」）：

```python
CAMP_CATEGORY_CONFIG = {
    'training': {
        'label': '培训营',
        'roles': ['student', 'mentor'],              # 本期实现
        'apply_windows': {'upcoming': ['mentor'], 'active': ['student']},
        'group_kinds': ['direction'],                # 大组，仅类别标签
        'selection': 'single_mentor',                # 学员选 1 导生（3 志愿）
        'multi_camp': True,                          # 学员可同时参加多个培训营
        'ms_enabled': True,
    },
    'project':   { ... Phase 2 定稿，见 §8.2 ... },
    'research':  { ... Phase 3 ... },
    'competition': { ... Phase 3，待与老师充分讨论 ... },
}
```

新增类型 = 开发人员加一个枚举值 + 一份配置 + 对应交互，老师无自建能力。

### 3.5 camp_member：从「成员表」泛化为「任职记录」（核心）

保留表名与现有外键（match/attendance_plan 等引用不动），扩展：

```python
class CampMember(db.Model):
    # 既有
    camp_session_id, user_id, joined_at
    role            # 枚举扩展：'student' | 'mentor' | 'project_lead' | 'research_lead'
                    #   Phase 1 只用到 student/mentor；后两个 Phase 2 启用
    team_mentor_id  # 培训营 student 行指向其导生；其余为 NULL（不变）
    # 新增（A6/A7）
    source          # 'apply'（报名审批）| 'assign'（后台指派）| 'legacy'（存量迁移）
    appointed_by    # FK user.id，NULL=legacy；审批人/操作人
    ended_at        # 结营回填
    evaluation      # TEXT NULL，预留：结营评语（老师或学员写）
    evaluated_by    # FK user.id NULL，预留
    # 约束
    #   删 UQ(camp_session_id, user_id)
    #   建 UQ(camp_session_id, user_id, role)
```

约束规则（应用层校验，按 category 配置执行）：

1. **同组不重复**（A4）：同一组内一人一职；不同组可兼任（学员+导生 / A 项目组长 + B 项目成员）。培训营的具体校验：student 行的 `team_mentor_id` 必须是本营 mentor（现状已有）；同一人同营可既有 mentor 行又有 student 行，但 student 行的导生不得与自己同大组（`camp_mentor_profile.group_id` 对比）。
2. **培训营学员行每营一条**（UQ(camp,user,role) 已保证）。
3. Phase 2 项目营把唯一键升级为 `(camp, user, role, group_id)` —— 届时 `team_mentor_id` 语义由显式 group 承接，本表不再改结构，只改约束与校验（设计上已预留）。

审批通过/后台添加的落库路径统一走 `_assign_member(role, source, appointed_by)`；结营（active→archived）时批量回填 `ended_at`。**历史 CampMember 行就是天然的任职档案**，迁移时补 `source='legacy'` 即可，无需回填。

### 3.6 camp_group（新表，V1 只用大组）

```python
class CampGroup(db.Model):
    id, camp_session_id(FK), kind('direction'|'project'|'department'), name, sort_order, created_at
    UQ(camp_session_id, kind, name)
```

- **V1（培训营）**：`kind='direction'` 大组仅是类别标签（软件组/硬件组…），**无组长、无管理功能**（A13-1）；super_admin 在营期详情里简单 CRUD（名称/排序）。
- 导生绑定大组：`camp_mentor_profile.group_id`（见 §3.7）。
- 学员的大组 = 读时推导（`student → team_mentor → mentor_profile.group_id`），**不冗余存储**，名单导出时 join。
- `kind='project' / 'department'` 为 Phase 2/3 预留，本期不建行。

### 3.7 camp_mentor_profile：名片与内部容量

| 变更 | 内容 |
|---|---|
| `+ group_id` | FK `camp_group.id` NULL——导生所属大组（一个导生一个大组，A13-1） |
| `capacity` | 降级为**内部字段**：仅 super_admin 与导生本人可见，**学员端一律不展示**（A9）。名片墙排序改为 `sort_order/姓名`，删除「按余量排序、满员沉底」逻辑；「剩余名额」「已满」标记全部下线 |
| 其余 | `photo / bio / tags`（名片装饰）不动；UQ(camp,user) 不动 |

名片编辑时机（纪要第 11 条）：upcoming 期报名导生获批后即可装饰，active 期可继续改。

### 3.8 camp_join_request：统一报名入口（学员入营 + 导生应募）

| 变更 | 内容 |
|---|---|
| `+ apply_role` | `VARCHAR(20) DEFAULT 'student'`，取值 `student / mentor`（Phase 2 扩展 `project_lead` 等） |
| 窗口规则 | 按 §3.4 `apply_windows`：upcoming 期接受 mentor 报名；active 期接受 student 报名。超出窗口 400 |
| 其余 | `reason / selected_days / status / reviewed_by / reviewed_at` 与审批流复用现状；学员手选承诺出勤日展开为 CampAttendancePlan 的逻辑不变 |

审批通过 → `_assign_member(role=apply_role, source='apply', appointed_by=审批人)`。老师后台也可直接拉人（`source='assign'`）。有意不加 UQ(camp,user) 的现状保留（rejected 可重报）。

### 3.9 选导生（camp_ms）：单轮志愿 + 导出 + 批量指派

**方向（A8/A10/A11）**：系统只负责「收集志愿、呈现数据、回填结果」，选择与调剂全部线下。流程：

```
upcoming：导生报名 → 老师审批 → 导生装饰名片、选大组
active 开营：学员报名入营 → 志愿窗口内提交 3 志愿（仅选导生，不选组；组从导生继承）
窗口关闭：老师导出 CSV → 线下与导生们选择/调剂 → 老师在后台批量指派回填
完成：/matched 出结果；team_mentor_id 与大组继承生效 → 进入学习/考勤
```

具体改造：

| 项 | 处理 |
|---|---|
| 阶段机 `_ms_phase` | 简化为 `disabled → collecting → done`（读时计算，依据 `mentor_selection_enabled` 与 `ms_preference_start/deadline`）；round1/round2 状态删除 |
| `camp_mentor_preference` | 表不动；`round` 列恒为 1（新数据），旧数据的 round=2 行仅存档不再读 |
| **删除** | `/pick`（导生系统内收人）、轮次推进相关端点与前端 MsMentorDesk 的收人交互；admin「立即截止一轮/跳过二轮」按钮 |
| **保留** | `/mentors` 名片墙、`/preferences`（提交志愿）、`/suitors`（导生看谁报了我——线下调剂时的名单视图，改只读）、`/assign`（单人指派）、`/matched`、`/results`、`/overview`（老师总览） |
| **新增** | ① `GET /camp/ms/<sid>/export`：CSV 宽表，每学员一行：`学员, 志愿1, 志愿2, 志愿3, 留言汇总, 当前已分配导生`（super_admin）② `POST /camp/ms/<sid>/assign/batch`：`{pairs:[{student_user_id, mentor_user_id}]}` 批量回填；校验学员未分配、导师为本营 mentor；幂等（跳过已分配行，返回成功/跳过/失败明细） |
| 防羊群红线 | 名额与志愿数均不再对外展示，红线自然消失；保留「不展示他人志愿数」作为后续红线 |
| e2e | `e2e/camp-market.spec.js` 同步改造（删收人用例，加导出/批量指派 mock 用例） |

调剂跨组与否、导生容量给不给建议值——全部线下自治，系统不感知（A8/A9/A11）。

### 3.10 课程与学习记录

| 项 | 决策 |
|---|---|
| `CourseModel` | **不动**。课程是独立实体，独立页面维护（A14-2；即纪要「课程页面单独维护」） |
| 自主加入学习 | **移除**：删 `POST /userCourse/enroll` 端点与前端「加入学习」按钮（`CourseDetailsComponent.vue`）；课程浏览/详情保持公开可见，但无学习入口 |

## 4. RBAC 与权限

### 4.1 A5-1 的答复：常见门户系统怎么做，本设计怎么选

通用做法有两派：**(a) 扁平超管 + 细粒度权限 ACL**（超管一个角色，用 permission 表区分能干什么——WordPress/Discourse 风格）；**(b) 多级管理员**（owner/admin/operator…分层）。对内部小系统，行业惯例是 (a)：角色层级越少越好，「谁」用 ACL 收，"为什么这么操作"靠审计。

本设计采纳 (a)，且**我们已经有现成的 PermissionModel/UserPermissionModel ACL**（`check_permission` 那套，seed 里已有 `camp_management` 等权限）：

- `role = super_admin / user` 两级；super_admin 直通一切（现状 `is_admin_like`）。
- 老师与开发人员**同为 super_admin**，差异只体现在：
  - `admin_tag`（teacher/developer）→ 审计日志与 admin 界面显示；
  - 未来若要限制开发人员触碰业务数据，用现有 ACL 给个别账号收紧（无需新角色）。
- 营内权限一律不看 `user.role`，看 `camp_member` 行（§4.2）。

### 4.2 门禁装饰器改造（`blueprints/__init__.py`）

| 装饰器 | 现状 | 改造后 |
|---|---|---|
| `camp_role(*roles)` | 查**全局** `user.role` ∈ roles | **重写为营内任职检查**：当前用户在本营 `camp_member.role` ∈ roles；super_admin 恒通过。营 id 从 view args 的 `<sid>` 取。语义变了但函数名保留，调用处只改参数（如 `@camp_role('mentor','super_admin')` → `@camp_role('mentor')`） |
| （新增）`admin_only()` | — | 全局 super_admin 检查，用于建营/发布/开营/归档/导出/批量指派/角色管理 |
| `check_permission(name)` | ACL 查询 + super_admin 直通 | 不动 |
| `_visible_student_ids` / `_in_my_team` | 已按 camp_member 团队收敛 | 不动（这正是解耦后的标准范式） |
| `camp_team_scoped` | 注释里预告、未实现 | 仍不实现（团队级校验继续手写在端点内） |

`camp.py` / `camp_ms.py` 全部门控按 §4.4 矩阵重写一遍（这是 Phase 1 的主要工作量之一）。

### 4.3 旧门禁一次性全量清账（2026-09-01 决策，推翻初稿「保留双写」）

初稿曾主张保留 `user_mode` 双写、让约 30 处裸门禁「恰好继续正确」。经与用户确认改为**一次性清账**：正确性不再依赖巧合，`user_mode` 彻底退役。

**盘点（2026-09-01 grep 实测）**——裸门禁约 48 处，分布于 9 个蓝图：

| 蓝图 | 处数 | 典型模式 |
|---|---|---|
| information.py | 13 | `is_admin = (user.user_mode == 'admin')`；`group.teacher_id != user.id and user_mode != 'admin'`（owner-or-admin） |
| course.py | 11 | `mode = user.user_mode` 后分支判断；owner-or-admin |
| discussion.py | 9 | `author_id != user.id and user_mode != 'admin'`（删帖/删回复 owner-or-admin） |
| learningProgress.py | 5 | `mode = user.user_mode` 分支 |
| notification.py | 3 | `show_all and user_mode == 'admin'` |
| homeCover.py | 3 | `mode = user.user_mode` 分支 |
| attendance_report.py | 2 | `!= 'admin'` 拒绝 |
| community.py / ai_topic.py | 各 1 | `== / != 'admin'` |
| （合计） | **48** | 另：information.py:1234 是 debug print，顺带删 |

非门禁引用（同步清理）：`auth.py:106`、`user.py:95/201/237`、`permissionACL.py:204`（payload 暴露 `User_Mode`/`user_mode`，删键——**前端 grep 零引用，删了不影响任何页面**）；`seed.py` 造号双写；`models.py:26` 列定义。

**替换规则（唯一收口）**：

1. 所有 `user_mode == 'admin'` / `!= 'admin'` → 统一走 `user.is_admin()`（现有 `is_admin_like()` 收敛后即此语义，禁止逐处裸写 `role == 'super_admin'` 字符串比较——未来再变只改 helper 一处）。
2. owner-or-admin 模式 → `if obj.owner_id != user.id and not user.is_admin(): return 403`（语义不变）。
3. `mode = user.user_mode` 分支型 → 逐处读上下文改写为 `is_admin()` 布尔（不保留三值思维）。
4. payload 删键、seed 删字段、models 删列（migrate_10 DROP COLUMN，回滚脚本可恢复）。

**为什么安全（等价性论证）**：`user_mode` 只有 'admin'/'user' 两值，收敛后 `user_mode=='admin'` ⇔ `role=='super_admin'`，替换是**恒等变换，零行为变化**。唯一前提是存量数据满足该等价——migrate_10 preflight 显式校验：`role ∈ {super_admin, teacher}` 与 `user_mode=='admin'` 的集合差异计数必须为 0，不为 0 则列出差异行人工裁定后再刷。把「巧合正确」变成「已验证正确」。

**验收（三条硬指标）**：

1. 零引用：`grep -rn user_mode --include='*.py'` 除 `scripts/migrate/*` 外 = 0；
2. 冒烟矩阵：9 个蓝图各抽关键路径 × {super_admin 放行, 普通用户 403}，重点 course 编辑/删除、discussion 删帖（owner-or-admin 型最易改错）；
3. 既有 e2e 全绿（前端本就不读 user_mode）。

清账与 §4.2 的 `camp_role` 重写同属 Phase 1a（§8.1），一次迁移内完成，不存在「半迁移」状态。

## 9. 风险与开放问题

| # | 风险/开放项 | 应对 |
|---|---|---|
| 1 | 单轮志愿 + 线下调剂 → 老师线下工作量大 | 导出宽表 + 批量指派尽量压缩操作成本；若实际跑一届后老师反馈要系统内反选，再评估恢复简化版 pick |
| 2 | Q15 未决（学习进度跨期语义） | Phase 2 项目营动工前必须定，否则 user_course UQ 会让跨期项目课丢营期戳 |
| 3 | 无角色管理端点（现状） | 已列入 Phase 1 #2，缺它无法任命新管理员 |
| 4 | `camp_role` 语义重写波及 camp.py/camp_ms.py 全部端点 | 逐端点对照 §4.4 矩阵重写 + e2e；这是 Phase 1 最大工作量，优先做、早做 |
| 5 | ms 删轮次涉及已上线交互，暑期营刚用过 | 迁移即强制结营，无兼容窗口；前端同步删 UI，不留半旧入口 |
| 6 | 约 48 处裸 user_mode 门禁清账，替换错一处即权限回归 | 替换是恒等变换（§4.3 等价性论证）+ preflight 校验存量一致性 + 零引用 grep 验收 + 9 蓝图两角色冒烟矩阵；owner-or-admin 型（course/discussion）逐处人工过目 |
| 7 | NAS / 比赛营 / 换组 / 等级系统未明 | 显式出范围（§1.2），需求明确后再入期 |
| 8 | check_record.camp_session_id 继续空置 | 已知债，本方案不动；若未来要「按营出勤报表」再落实写入 |
