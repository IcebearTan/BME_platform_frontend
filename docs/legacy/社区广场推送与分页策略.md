# BME 社区广场：内容推送策略 & 分页策略设计

> 范围：`BME_platform_flask`（后端）+ `BME_frontend`（用户端）的社区广场 `/community` 与聚合接口 `/community/feed`。
> 事实依据核对至 2026-08-02 最新代码（flask `6524fad` / frontend `f855bca`）。
> 决策记录：治理走**轻量降权**路线（不做发帖审核队列）；近期落地范围 = **P0**。

---

## 一、背景与问题

社区广场当前混合展示「global 讨论帖 + v1 文章 + v2 文章」三类内容，存在三类痛点：

1. **文章侧荒芜**：优质长文随时间被埋，新文章又少有人发，呈现"一堆古董 + 几条灌水"。
2. **讨论侧灌水**：发帖零门槛（标题/正文 1 字符即过、无频率限制、立即公开），低质内容上浮。
3. **体感慢/重**：被描述为"一次性加载所有"，实际根因不是没分页，而是性能炸弹（见下）。

## 二、根因诊断（已核对实际代码）

**根因 1 —— 后端"假分页 / 内存分页"**（`blueprints/community.py:134-254`）
`/community/feed` 虽接收 `page/per_page`，但内部先 `query.all()` 把三类内容**全表加载进内存** → 排序 → 再 `items[start:start+per_page]` 切片。**每次请求都全量加载 + 全量排序**，分页只省了下发体积，没省查询/排序成本。

**根因 2 —— 前端 N+1 请求炸弹 #1**（`CommunityView.vue:382-405` `enrichDiscussion`）
拉一页后对**每条讨论帖**单独发 `GET /discussions/threads/{id}/replies` 拉内联回复。一页 20 条 ≈ 最多 20 个并发请求。是广场"慢/卡"的最直接原因。

**根因 3 —— 前端 N+1 请求炸弹 #2**（`DiscussionCard.vue:148-176` `onMounted` IntersectionObserver）
每张卡进视口就调 `GET /discussions/threads/{id}` 详情接口拿 view/like/reply_count——而这些 feed 已返回，属冗余请求；且它让 `view_count` 沦为"卡片在 feed 挂了多久"的噪声，形成"高热度→排前→展示更多→浏览更高→热度更高"反馈循环。

**根因 4 —— 热度公式结构性埋葬文章**（`community.py:194-198`）
文章互动分 `_interaction = 2 * 评论数`，**不含点赞、不含浏览**。文章天然评论少 → 互动分趋零 → 14 天半衰期后热度趋零 → 沉底 → 无人看 → 无新评论，死循环。

**根因 5 —— 零发帖门槛 + 自助置顶漏洞**
- `discussion.py:258` 只判非空，1 字符也过；无最小长度、无频率限制、无反垃圾、立即 `status=normal` 公开。
- `discussion.py:142-152` `can_moderate_thread`：作者可置顶/锁自己的帖子（被 pin `L531` / lock `L561` 复用）。注：删帖 `L52` / 编辑 `L14` 用的是独立内联检查，不受影响。

> 结论：当前缺的不是"分页"，而是 **「质量无分层 + 内容无分类 + 性能有 N+1」** 三件事叠加。

## 三、分页策略（治性能）

按"量级未到 SQL 真分页临界点"的现实，分两档推进：

### P0：消灭 N+1 + feed 短缓存（立竿见影）
- **N+1 #1 消除**：feed 接口直接**附带每条讨论帖前 2 条回复预览**。后端对**当前页**的讨论帖 thread_id 用 `DiscussionReply.thread_id IN (...)` **一次查回**（走 `idx_reply_thread` 索引），Python 分组取前 2 条；前端删掉 `enrichDiscussion` 的逐帖请求。一页请求从 1+20 降到 **1**。
- **N+1 #2 消除**：删 `DiscussionCard` 的 IntersectionObserver 详情请求；卡片直接用 feed 返回的 view/like/reply_count。顺带净化 view_count 噪声。
- **feed 短缓存**：用现成 `redis_client`（`exts.py`），缓存"排序+切片后的公共 items"（不含用户特定 `liked`），key=`feed:{type}:{sort}:{page}:{per_page}:{view}`（view=admin/public），TTL 8s；命中后回填当前用户 liked。
  - 降级：若公共缓存复杂度超预期，退化为 per-user 整响应缓存，或先只做 N+1 消除。

### P2：hot_score 入库 + union 真分页（量级破万再做）
- 三模型加 `hot_score` + `rank_at` 列，定时任务（10 分钟级）重算半衰期。
- 查询时三类 union `ORDER BY hot_score DESC LIMIT/OFFSET`，彻底摆脱内存全量排序（Reddit/HN 路线）。
- **现在做是过度工程**，等内容破万或 feed 慢到不可接受再上。

> 短期结论：分页的答案 = 干掉 N+1 + 加缓存，**不是**重写 SQL 真分页。

## 四、推送策略（治质量与活跃度）

### P1：修热度公式（核心）
| 内容 | 互动分 I | 半衰期 |
|---|---|---|
| 讨论帖（现状） | `点赞 + 2*回复` | 14 天 |
| **文章（改）** | `2*评论 + 1*点赞 + 0.3*浏览` | **30 天** |

- 文章可安全用 `view_count`：讨论帖的 view 被视口污染（根因 3），但**文章浏览是点进详情页才计的真实阅读**，性质不同。
- 文章半衰期拉到 30 天：教育长文是长尾内容，两周前的好文不该输给昨天零互动的新帖。
- 浏览系数压到 0.3 配幂等去重（`discussion.py:416` 已有），防刷。

### P1：质量分层（轻量降权路线，不做审核队列）
- **作者权重**：复用现成 RBAC（四级角色 super_admin/teacher/mentor/student）。教师/mentor 发的内容热度 ×1.5，student ×1.0——灌水主力天然下沉。
- **精华标记**：新增 `is_essence` 字段（或复用 `is_pinned` 语义区分）；管理员/教师标记，热度 ×2，并进广场顶部"精选"位。
- **新内容曝光保护**：发布 24h 内给额外基础分（现公式 `+1` 可提到 `+3`），保证新内容有曝光窗口——激活更新的杠杆。

### P1：复活运营位
`CommunityView.vue:44` 被 `v-if="false"` 禁用的 banner、侧栏残留的 `active-user-item`/`topic-item`，不是要删的旧码，而是**没接真的运营位**。接成：本周精选 / 待回答的问题 / 活跃作者，打破单一时间线。

## 五、质量治理（治灌水，轻量降权）

### P0（低成本高收益）
- **发帖最小长度**：讨论标题 ≥ 4 字、正文 ≥ 10 字（strip 后计）；回复 ≥ 2 字。
- **发帖频率限制**：用现成 `redis_client` 手动计数（key=`post_rate:{user_id}`，INCR+EXPIRE），如 5 分钟 ≤ 3 帖、小时 ≤ 10 帖。
  - 不用 `@limiter.limit` 按用户限流：limiter 在 `before_request` 跑、jwt 在视图级才解析，`key_func` 拿不到用户身份；手动 redis 更可靠。
- **修自助置顶漏洞**：`can_moderate_thread` 去掉"作者可管自己"（删 `L151-152`），仅 admin（可扩展教师）。已确认只影响 pin/lock，作者删/编辑权不受影响。

### P1
- **低质量折叠**：正文 < 阈值 **且** 7 天零互动的帖，feed 默认折叠进"低活跃"区（不删，降权到几乎不曝光）。
- 管理端给隐藏/精华一个轻量操作面板（`status` 的 hidden 已可用，加 essence 即可）。

## 七、P0 详细实现方案（已核对，待执行）

### A. 消灭 N+1 #1 —— feed 附带回复预览
**后端 `community.py`**（`community_feed` 切片后，L254 之后）：
- 收集 `page_items` 里 `type=='discussion'` 的 thread_id 集合。
- 一次查询：`DiscussionReply.query.filter(thread_id.in_(ids), parent_reply_id=None, status=STATUS_NORMAL).order_by(DiscussionReply.created_at.desc()).limit(200)`，Python 按 thread_id 分组取前 2 条并还原成正序。
- 回复字段结构对齐 `list_replies`（`discussion.py:721`）：`{id, author_id, author_name, author_avatar, content, like_count, liked, created_at}`；`author_avatar` 复用 `community.py:37` 现有 `get_avatar_url`。
- reply 级 `liked`：批量查当前用户对这些 reply 的点赞（参照 `list_replies:700-706`）。
- 讨论帖项新增 `"replies": [...]`；文章项不带（评论在详情页看）。
- import 补 `DiscussionReply`。

**前端 `CommunityView.vue`**：
- 删 `enrichDiscussion`（L382-405）及其 `Promise.all` 调用（L473）。
- `raw.map` 的 discussion 分支新增 `replies: (item.replies||[]).map(r => ({...r, time: formatTimeAgo(r.created_at)}))`。

**前端 `DiscussionCard.vue`**：
- L63 `全部回复 ({{ discussion.replies.length }})` → 基于 `discussion.reply_count`；预览数 < reply_count 时显示"查看全部 N 条回复"。

### B. 消灭 N+1 #2 —— 删 DiscussionCard 详情请求
**前端 `DiscussionCard.vue`**：
- 删 `onMounted` IntersectionObserver（L148-176）整块；卡片直接用 `props.discussion.views/like_count/reply_count`（CommunityView 已映射）。
- 影响：讨论帖 view_count 不再因进视口 +1（消除噪声埋点）；真实计数增长留 P1。

### C. feed 短缓存
**后端 `community.py`**：
- `from exts import db, redis_client`。
- 抽 `_build_feed_page(type, sort, page, per_page, is_admin)` 返回**不含 liked** 的公共 items。
- key=`feed:{type}:{sort}:{page}:{per_page}:{view}`，TTL 8s，JSON 存 redis。
- 命中后遍历当前页回填 liked（讨论帖 `id in liked_thread_ids`；v2 文章 `tid in liked_thread_ids`）。
- 不做主动失效（8s TTL 足够）。

### D. 发帖校验 + 频率限制 + 修自助置顶
**后端 `discussion.py`**：
- `create_thread`（L241）：L258 非空校验后加 title ≥ 4 字、content ≥ 10 字（strip 后），返 400。
- `create_thread` 视图内（jwt 已解析）用 `redis_client` 手动计数限流：5 分钟 ≤ 3、小时 ≤ 10，超限返 429。
- `can_moderate_thread`（L142）：删 L151-152"作者可管自己"，仅留 admin。
- `create_reply`（L584）：content ≥ 2 字（可选加频率）。

## 八、风险与回滚
- feed 加 `replies` 是**新增字段**，第二调用者 `StudyHub.vue`（`/community/feed` sort=latest，不读 replies）不受影响 → 向后兼容。
- 删 IntersectionObserver：view_count 停滞（可接受，本就噪声）；需保留计数可回滚该块。
- `can_moderate_thread` 改动：已确认仅影响 pin/lock，作者删/编辑权不变。
- 缓存 TTL 8s：最坏 8s 看到新帖，可接受或调小。
- **全部改动不碰 DB schema（无 migration）** → 回滚 = 改回代码。

## 九、验证（实现后）
- **后端**：`GET /community/feed?type=all&sort=hot&page=1` → discussion 项有 `replies`（≤2 条）、article 项无；二次请求走缓存。`POST /discussions/threads`：title 3 字→400、content 5 字→400、正常→201；连续超限→429；非 admin 作者 pin→403、admin→200。
- **前端**：进 `/community`，Network 翻页仅 1 个 `/community/feed`（无 N 个 replies/详情 请求）；讨论卡显示回复预览 + "查看全部 N 条"；StudyHub 首页动态正常。
